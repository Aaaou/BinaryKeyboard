# CH592F 2.4G 固件测试说明

## 构建产物

在 `firmware/CH592F` 目录执行：

```text
cmake -S . -B build/2g4-5key -G Ninja -DCMAKE_BUILD_TYPE=MinSizeRel -DKEYBOARD=5KEY -DKBD_RADIO_2G4_ENABLED=ON
cmake --build build/2g4-5key

cmake -S . -B build/2g4-knob -G Ninja -DCMAKE_BUILD_TYPE=MinSizeRel -DKEYBOARD=KNOB -DKBD_RADIO_2G4_ENABLED=ON
cmake --build build/2g4-knob

cmake -S . -B build/receiver -G Ninja -DCMAKE_BUILD_TYPE=MinSizeRel -DKBD_RECEIVER_BUILD=ON
cmake --build build/receiver
```

对应镜像：

- `build/2g4-5key/CH592F-2G4-5KEY-full.hex`：5 键键盘 2.4G 首次 ISP 整包
- `build/2g4-knob/CH592F-2G4-KNOB-full.hex`：旋钮键盘 2.4G 首次 ISP 整包
- `build/2g4-5key/CH592F.hex`、`build/2g4-knob/CH592F.hex`：仅从 `0x1000` 开始的键盘应用镜像；不能用于整片擦除后的首刷
- `build/receiver/CH592F-RECEIVER-full.hex`：CH592F 接收器首次 ISP 烧录整包
- `build/receiver/CH592F.hex`：仅从 `0x1000` 开始的接收器应用镜像，不能用于整片擦除后的首刷
- `build/receiver-usb-diagnostic/CH592F-RECEIVER-USB-DIAGNOSTIC-full.hex`：仅用于排查 USB 枚举；不启动 RF，不作为 2.4G 功能验收固件
- `build/receiver-time-diagnostic/CH592F-RECEIVER-TIME-DIAGNOSTIC-full.hex`：阶段 1 接收器诊断包；启动 32 kHz/RTC/TMOS 时间基准，但不启动 RF 库、TMOS 主循环或 RF Host
- `build/receiver-rf-library-diagnostic/CH592F-RECEIVER-RF-LIBRARY-DIAGNOSTIC-full.hex`：阶段 2 接收器诊断包；在阶段 1 基础上初始化 RF FAST 库并运行 TMOS，但不启动 RF Host 或配码

普通 release 构建没有链接 RF FAST 库，也不会显示 2.4G 能力。

## 当前硬件验证状态

目前可确认 USB 诊断接收器能够被 Windows 和 Studio 作为 Vendor HID 设备稳定访问。该诊断固件不会启动 RF、TMOS 或配码状态机，因此不能配码，也不能接收键盘输入。

正式 RF 接收器在启动 RF 初始化后出现 USB 掉线，正在分阶段定位 `HAL_TimeInit`、`RF_LibInit` 与 Host 启动之间的原因。没有完成该定位和双板实测前，不应刷写正式接收器来验收 2.4G 功能，也不应把当前键盘 2.4G 固件用于实际配码。

## 先做可观察的启动诊断

所有接收器诊断包都会把启动事件保留在 RAM。Studio 识别到接收器后会通过 `LOG_GET` 逐条读取并显示这些已保留的事件；这不是依赖浏览器时机的异步日志推送。因此不需要抢在插入 USB 的瞬间打开网页，也不会因为浏览器尚未连接而丢失启动日志。

阶段 1 已验证时间基准完成。下一步硬件测试只刷写 `build/receiver-rf-library-diagnostic/CH592F-RECEIVER-RF-LIBRARY-DIAGNOSTIC-full.hex`。刷写完成后拔掉下载器，接收器直接插入电脑，打开 Studio 并连接该设备，然后打开 Debug Terminal。必须看到以下顺序：

1. `接收器启动 | 阶段 1`
2. `USB 已配置 | 阶段 1`
3. `时间基准初始化开始 | 阶段 1`
4. `时间基准初始化完成 | 阶段 1`

这四项均出现且设备保持在线至少 60 秒，才可以继续阶段 2。若只到 `USB 已配置`，问题就在 `HAL_TimeInit()` 内部或其触发的时钟/中断；若四项均出现后设备掉线，日志截图仍可确认时间初始化已经返回，后续检查主循环和 USB/RF 资源冲突。

只有阶段 1 保持在线，才继续刷写阶段 2。阶段 2 的日志必须在上述四项之后继续出现 `RF 库初始化开始 | 阶段 2` 和 `RF 库初始化完成 | 阶段 2`。阶段 2 保持在线说明 `RF_LibInit` 本身没有破坏 USB，故障位于 Host 启动或之后的 RF 收包处理；阶段 2 掉线且没有“完成”记录则停止测试阶段 3，检查 RF 库的中断、DMA、时钟和 RAM 使用。

阶段 3（`build/receiver/CH592F-RECEIVER-full.hex`）的日志会额外给出 `RF Host 初始化开始`，之后只能是 `RF Host 初始化完成` 或 `RF Host 初始化失败 | 结果 n`。只有阶段 3 保持在线、日志显示 Host 完成、并且完成键盘实际配码及输入测试后，正式接收器才可以被称为可用。Studio 的“接收器状态”会显示当前启动阶段；阶段 0/1/2 不展示配码入口，也会立即拒绝配码写命令。

## 完成正式联调后的首次配码流程

1. 接收器首次烧录必须使用 `build/receiver/CH592F-RECEIVER-full.hex`，然后插入电脑。
2. 无绑定记录时，接收器自动进入 60 秒配码窗口。
3. 键盘刷入对应 2.4G 镜像，打开电源；通过 Studio 的 Wireless 面板点击“开始配码”。
4. 配码成功后，键盘和接收器都把对端地址写入 DataFlash。之后拔插、重启不需要重新烧录。
5. Studio 读取到 `radio2g4=1` 且角色为 `receiver` 时，显示接收器的配码、清除绑定和轮询率控制。

接收器绑定和轮询率使用 DataFlash 保留区 `0x5000/0x5100` 的双槽记录，带版本、代数和 CRC16；不会占用键盘已有的配置槽、宏区、IAP 标志或 BLE SNV。写入时先写备用槽并回读校验，掉电时启动自动选择最近的有效槽。

## 指示与状态

当前 RF 固件的可靠状态来源是 Studio 的 `RADIO_PAIR_STATUS`，不是 RGB 颜色。配码窗口和成功/失败灯效仍应由具体板级 RGB 适配层接入后再作为验收条件；本提交没有伪造“已经联调过的灯效”。

## 清除与重新配码

- 清除接收器：Studio 对接收器执行“清除绑定”。接收器会清空 DataFlash，并立即回到配码窗口，不会变成废接收器。
- 清除键盘：Studio 对键盘执行“清除绑定”。接收器端原记录仍存在，此时状态会变为未连接；应随后在接收器上执行一次“清除绑定”，再重新配码，避免单边残留。
- 取消配码：只停止当前配码，不删除已有有效绑定。

## 轮询率

可选 `125 / 250 / 500 / 1000 Hz`，默认 `1000 Hz`。设置写入接收器 DataFlash；USB 报告由接收器按该节奏合并提交，RF 链路仍由官方 RF FAST Host 状态机负责。

接收器的 RF/USB 中断只入队或设置控制标志，Flash 擦写、重新配码和 USB 报告发送均在主循环执行；USB 键盘、鼠标、消费者端点都使用 1 ms 描述符间隔。RF 包按 session/sequence 去重。HID 全释放只在 RFBound 正式报告断链或失败后执行；正常空闲时没有新的应用层 HID 包，不会被当成断联。

## 当前验证边界

已通过 CH592F 交叉编译、链接和 `git diff --check`。普通 5KEY/KNOB、2.4G 5KEY/KNOB 和 Receiver 五个目标均可生成 `.hex`。官方 RF FAST 库与 BLE 库存在同名基带实现，因此 2.4G 键盘是独立 RF-only 镜像，不能与 BLE 协议栈同时链接。真实配码、距离、丢包率、断电恢复和功耗仍需要两块 CH592F 实物联调后确认。
