# CH592F 2.4G 固件测试说明

## 接收器冻结基线（2026-09-03）

2026-09-03 的管理透传与重连清理修复已经在标准接收器和键盘改作的接收器上重新
完成配码、HID、远端读写及断电重连验收。从该版本开始，在新接收器硬件和新的量产
需求出现前，接收器固件重新按“一次烧录、装配后永久运行”冻结：

- 接收器后续不再跟随键盘提交修改；键盘端可以继续迭代。
- 首刷只认 `CH592F-RECEIVER-full.hex` 或同名 `.bin`，由工厂 ISP 夹具完成；它包含
  接收器专用 JumpIAP 跳板和接收器应用，不包含高地址 IAP。
- 接收器专用跳板固定直接跳到 `0x01000`；不会再跳到 `0x6D000`，也不会保留
  USB IAP 写 Flash 的入口。
- 每次接收器镜像变更都必须重新经过 Bootloader 入口、USB、RF、配码和 HID 全套
  验收后才能替换生产基线。
- 接收器板必须在装配前保留一次可进入 ROM Bootloader 的工厂夹具或测试焊盘；拆线后
  无法进入 ROM 是硬件维护边界，不能由网页或普通软件复位补出来。

## 接收器量产维护要求（永久 ISP 基线）

接收器移除 ISP 飞线、装入外壳后，固件按“一次烧录、永久运行”处理：网页不显示
固件更新入口，接收器不实现 USB IAP/OTA，也不发布 `CH592F-RECEIVER-app.bin`。
后续只允许修改键盘固件和网页；接收器只有在出现新硬件或明确的量产返工时，才由
工厂恢复 BOOT 入口后重新 ISP 烧录新的完整包。

拆飞线前必须完成一次完整验收：整片 ISP 烧录、USB 枚举、配码、HID 输入、拔插恢复
和 DataFlash 配对记录保留。拆线后无法进入 ROM ISP 是硬件维护边界，不能由网页或
普通软件复位补出来。

> **已知限制（发布前必须保留）：断联后的按键释放不是已解决问题。**
>
> 我们依次试过应用层 KEEPALIVE、短周期应用看门狗、Timer 强制释放以及
> `RFRole_Shut -> RF_LibInit` 主动重连。实测它们会造成误判断联、填满 RF
> TX 描述符，或打断 WCH RFBound 自己的恢复流程，均已撤回。当前版本严格
> 按 WCH 官方 RFBound 语义运行：`bleTimeout` 交给库内部恢复，只有
> `FAILURE` 才重启保存的 Host/Device。
>
> 因此，键盘在断电或接收器消失前没有发送松开报告时，电脑可能继续重复最后
> 一个按键约 **5 秒**，直到 RFBound 到达终止失败并触发接收器的全零 HID
> 释放。这个边界在官方参考实现中同样存在；当前工程**无法把它保证为
> 400 ms 或更短，也不能宣称已经修复**。测试时请把“最终会停止”与“停止
> 延迟”分开记录。

## 构建产物

在 `firmware/CH592F` 目录执行：

```text
cmake -S . -B build/2g4-5key -G Ninja -DCMAKE_BUILD_TYPE=MinSizeRel -DKEYBOARD=5KEY -DKBD_RADIO_2G4_ENABLED=ON
cmake --build build/2g4-5key

cmake -S . -B build/2g4-knob -G Ninja -DCMAKE_BUILD_TYPE=MinSizeRel -DKEYBOARD=KNOB -DKBD_RADIO_2G4_ENABLED=ON
cmake --build build/2g4-knob

cmake -S . -B build/receiver -G Ninja -DCMAKE_BUILD_TYPE=MinSizeRel -DKBD_RECEIVER_BUILD=ON
cmake --build build/receiver
```

生产接收器建议使用统一构建脚本生成整套产物：

```text
python tools/scripts/ch592f.py build-full --keyboard RECEIVER --profile release
```

输出目录为 `firmware/CH592F/build/release-receiver/`，其中接收器正式发布只使用
`CH592F-RECEIVER-full.hex` 和同内容的 `CH592F-RECEIVER-full.bin`；不使用应用偏移包。

默认只向烧录人员展示以下正式完整包，每个目标同时提供 `.hex` 和 `.bin`：

- `CH592F-2G4-5KEY-full.hex/.bin`：5 键键盘 2.4G 首次 ISP 完整包
- `CH592F-2G4-KNOB-full.hex/.bin`：旋钮键盘 2.4G 首次 ISP 完整包
- `CH592F-RECEIVER-full.hex/.bin`：CH592F 接收器首次 ISP 完整包

`build-full` 仍会生成合并所需的 app、JumpIAP、IAP、ELF 和 MAP 中间文件，但终端
默认隐藏这些路径，避免把偏移应用包误当成首刷包。开发者需要检查中间文件时，可用
`artifact --type bin/hex/elf/map/iap_bin/iap_hex` 显式查询。构建目录整体已由
`.gitignore` 排除，不会随源码分支推送。

<details>
<summary>历史分阶段诊断包（仅故障定位时展开）</summary>

- `receiver-usb-diagnostic`：只验证 USB 枚举，不启动 RF。
- `receiver-time-diagnostic`：阶段 1，只验证 32 kHz、RTC 与 TMOS 时间基准。
- `receiver-rf-library-diagnostic`：阶段 2，额外初始化 RF FAST 库，但不启动 Host。

普通 release 构建没有链接 RF FAST 库，也不会显示 2.4G 能力。

## 实际验收流程

### A. 首次 ISP 烧录（必须先能进入 ROM Bootloader）

这一步不是把接收器当普通键盘插上 USB 就能完成。BinaryKeyboard ISP/WCHISP 只连接
已经进入 CH592F ROM Bootloader 的芯片。当前接收器固件没有软件强制进入 ROM 的命令，
`SYS_ResetExecute()` 也不会改变这一点。

1. 确认板上的 BOOT 选项字节和实际可控引脚一致：默认是 `PB22`，改过选项字节的板子
   可能使用 `PB11`。必须保留对应的 BOOT 飞线、按键或测试焊盘；若两根线都已拆除，
   不能进行首刷或救砖，必须先恢复其中一根硬件入口。
2. 断开接收器 USB，按住当前配置的 BOOT 引脚有效电平，再连接 ISP/USB 下载器；
   WCHISP 能识别到 CH592F 后再松开 BOOT。若仍找不到设备，先不要打开 Studio，
   这是 ROM Bootloader 入口问题，不是固件文件名问题。
3. 使用 BinaryKeyboard ISP，选择 CH592F，加载
   `firmware/CH592F/build/release-receiver/CH592F-RECEIVER-full.hex`。
4. 执行整片烧录并复位。`CH592F-RECEIVER-app.bin` 不能用于这一步。
5. 拔掉下载器，但暂时不要拆除板上的 BOOT 入口，接收器直接插入电脑。
6. Studio 连接设备后，在 Debug Terminal 确认出现：
   `USB 已配置`、`RF 库初始化完成`、`RF Host 初始化完成`。

### B. 拆飞线前的永久基线验收（发布门槛）

1. 保持接收器 USB 连接，在 Studio 确认角色显示为 `CH592F 2.4G 接收器`，不能显示
   为 5 键键盘。
2. 通过 `RADIO_CAPS`、`RADIO_PAIR_STATUS`、`SYS_STATUS` 读取能力、绑定和 Host
   阶段；接收器发来的 IAP 命令必须返回 `KBD_RESP_ERR_INVALID`。
3. 完成配码、HID 输入、接收器拔插和键盘重启测试，确认绑定记录保留。
4. 完成上述测试后再拆除 BOOT/ISP 飞线。拆线后只做 USB 枚举、状态、配码和 HID
   回归，不把软件升级作为接收器功能。

### C. 2.4G 功能验收

1. 接收器接电脑并保持供电，键盘刷入对应的
   `CH592F-2G4-5KEY-full.hex` 或 `CH592F-2G4-KNOB-full.hex`。
2. 两端已有旧绑定时，先分别执行“清除绑定”；接收器清除后会重新进入配码窗口，
   不会变成废接收器。
3. 在接收器的 Studio 页面点击“开始配码”，再给键盘上电并在键盘页面点击“开始配码”。
   配码窗口内两端均应显示对端 ID；`RADIO_PAIR_STATUS` 的本机/对端 ID 必须互相对应。
4. 配码完成后测试普通按键、长按、多个按键同时按下、接收器拔插、键盘断电再上电。
   接收器重启和 USB 重新插入不应清除绑定。

### D. 日志判定

Debug Terminal 至少应能读到：

```text
接收器启动 | 阶段 3
USB 已配置 | 阶段 3
RF 库初始化完成 | 阶段 3
RF Host 初始化完成 | 阶段 3
```

配码时再观察 `开始配码`、`配码事务成功`、`收到首个有效 RF 帧`；配码失败时记录
`RF 配码超时` 以及两端的 `RADIO_PAIR_STATUS`，不要只根据 RGB 颜色判断状态。

### 当前验收边界

接收器不提供 USB IAP，量产维护必须保留 ROM Bootloader 工装路径；在完成 B 步骤前
不能称为最终商业发布版。键盘突然断电且未发送松开
报告时，RFBound 可能需要约 5 秒才确认失败并发送全零 HID 释放；该限制按官方 RFBound
语义保留，不作为管理通道重连验收失败条件，但应单独记录。

## 先做可观察的启动诊断

所有接收器诊断包都会把启动事件保留在 RAM。Studio 识别到接收器后会通过 `LOG_GET` 逐条读取并显示这些已保留的事件；这不是依赖浏览器时机的异步日志推送。因此不需要抢在插入 USB 的瞬间打开网页，也不会因为浏览器尚未连接而丢失启动日志。

阶段 1 已验证时间基准完成。下一步硬件测试只刷写 `build/receiver-rf-library-diagnostic/CH592F-RECEIVER-RF-LIBRARY-DIAGNOSTIC-full.hex`。刷写完成后拔掉下载器，接收器直接插入电脑，打开 Studio 并连接该设备，然后打开 Debug Terminal。必须看到以下顺序：

1. `接收器启动 | 阶段 1`
2. `USB 已配置 | 阶段 1`
3. `时间基准初始化开始 | 阶段 1`
4. `时间基准初始化完成 | 阶段 1`

这四项均出现且设备保持在线至少 60 秒，才可以继续阶段 2。若只到 `USB 已配置`，问题就在 `HAL_TimeInit()` 内部或其触发的时钟/中断；若四项均出现后设备掉线，日志截图仍可确认时间初始化已经返回，后续检查主循环和 USB/RF 资源冲突。

只有阶段 1 保持在线，才继续刷写阶段 2。阶段 2 的日志必须在上述四项之后继续出现 `RF 库初始化开始 | 阶段 2` 和 `RF 库初始化完成 | 阶段 2`。阶段 2 保持在线说明 `RF_LibInit` 本身没有破坏 USB，故障位于 Host 启动或之后的 RF 收包处理；阶段 2 掉线且没有“完成”记录则停止测试阶段 3，检查 RF 库的中断、DMA、时钟和 RAM 使用。

阶段 3（`build/receiver/CH592F-RECEIVER-full.hex`）的日志会额外给出 `RF Host 初始化开始`，之后只能是 `RF Host 初始化完成` 或 `RF Host 初始化失败 | 结果 n`。只有阶段 3 保持在线、日志显示 Host 完成、并且完成键盘实际配码及输入测试后，正式接收器才可以被称为可用。Studio 的“接收器状态”会显示当前启动阶段；阶段 0/1/2 不展示配码入口，也会立即拒绝配码写命令。

## 完成正式联调后的首次配码流程

1. 接收器首次烧录必须使用 `build/receiver/CH592F-RECEIVER-full.hex`，然后插入电脑。
2. 无绑定记录时，接收器自动进入 60 秒配码窗口。
3. 键盘刷入对应 2.4G 镜像，打开电源；通过 Studio 的 Wireless 面板点击“开始配码”。
4. 配码成功后，键盘和接收器都把对端地址写入 DataFlash。之后拔插、重启不需要重新烧录。
5. Studio 读取到 `radio2g4=1` 且角色为 `receiver` 时，显示接收器的配码、清除绑定和轮询率控制。

接收器绑定和轮询率使用 DataFlash 保留区 `0x5000/0x5100` 的双槽记录，带版本、代数和 CRC16；不会占用键盘已有的配置槽、宏区、IAP 标志或 BLE SNV。写入时先写备用槽并回读校验，掉电时启动自动选择最近的有效槽。

## 指示与状态

当前 RF 固件的可靠状态来源是 Studio 的 `RADIO_PAIR_STATUS`，不是 RGB 颜色。配码窗口和成功/失败灯效仍应由具体板级 RGB 适配层接入后再作为验收条件；本提交没有伪造“已经联调过的灯效”。

## 清除与重新配码

- 清除接收器：Studio 对接收器执行“清除绑定”。接收器会清空 DataFlash，并立即回到配码窗口，不会变成废接收器。
- 清除键盘：Studio 对键盘执行“清除绑定”。接收器端原记录仍存在，此时状态会变为未连接；应随后在接收器上执行一次“清除绑定”，再重新配码，避免单边残留。
- 取消配码：只停止当前配码，不删除已有有效绑定。

## 轮询率

可选 `125 / 250 / 500 / 1000 Hz`，默认 `1000 Hz`。设置写入接收器 DataFlash；USB 报告由接收器按该节奏合并提交，RF 链路仍由官方 RF FAST Host 状态机负责。

接收器的 RF/USB 中断只入队或设置控制标志，Flash 擦写、重新配码和 USB 报告发送均在主循环执行；USB 键盘、鼠标、消费者端点都使用 1 ms 描述符间隔。RF 包按 session/sequence 去重。HID 全释放只在 RFBound 正式报告断链或失败后执行；正常空闲时没有新的应用层 HID 包，不会被当成断联。

## 当前验证边界

已通过 CH592F 交叉编译、链接和 `git diff --check`。普通 5KEY/KNOB、2.4G 5KEY/KNOB
和 Receiver 五个目标均可生成 `.hex/.bin`。官方 RF FAST 库与 BLE 库存在同名基带
实现，因此 2.4G 键盘是独立 RF-only 镜像，不能与 BLE 协议栈同时链接。实机已确认
配码、HID、远端配置读写、键盘断电重连和不同接收器硬件；距离、长期丢包率、功耗及
批量一致性仍需继续验收。管理透传失败和重连永久 `ERR_BUSY` 的根因与算法见
[2.4G 配码与接收器设计](./2.4g-pairing.md#远端配置透传协议)。

## 断联释放专项结论

- **已验证可以做到：** RFBound 恢复成功时保留绑定，不进入配码；Host 收到有效
  失败事件时清理旧接收数据并重新启动保存 peer；确认断链后接收器发送键盘、鼠标、
  消费者全零报告。
- **已验证做不到：** 在 RFBound 尚未报告终止失败前，仅凭应用层代码可靠判断
  “键盘已经断电”，并在 400 ms 内停止主机重复输入。此前所有主动方案都曾在
  实机上导致更严重的误断联或无法重连，因此不再作为发布固件方案。
- **发布措辞：** 必须写成“遵循 WCH RFBound 的自动恢复；断电断联的 HID 释放
  延迟受 RFBound 底层超时限制，实测约 5 秒”，不能写成“已实现快速断联释放”。
