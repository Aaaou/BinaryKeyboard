## 运行模式与轮询率

由于 WCH RF FAST 与 BLE 库包含冲突的底层基带实现，三模固件不是把两套库链接成一个 ELF，而是由 Dispatcher 在 USB/BLE 与 2.4G 两个应用镜像间切换。2.4G 子镜像沿用冻结的 RF-only 实现并保留 USB Vendor HID；架构与升级细节见[三模架构](./trimode.md)。

接收器使用 USB Full-Speed HID，支持 `125 / 250 / 500 / 1000 Hz`，默认 `1000 Hz`。设置入口是 Studio 的“2.4G 无线与接收器”，设置写入接收器 DataFlash。USB 描述符固定提供 1 ms 端点，较低轮询率由接收器合并报告实现。CH592F USB Full-Speed 的主机侧上限约为 1000 Hz，不提供没有实际收益的 2K/4K/8K 选项。

## 灯光状态

配码提示只写 LED0（独立指示灯）。多 LED 键盘的 LED1..LEDn 仍由按键 RGB
效果管理，不再由 RF 配码任务直接刷新，因此不会出现两颗灯被配码逻辑同时抢写：

| 状态 | 灯光 |
| --- | --- |
| 接收器无绑定，自动等待配码 | 蓝色双闪，约每秒一次，持续 60 秒 |
| Studio 或 FN 手动开始配码 | 蓝色慢闪，持续 60 秒 |
| 配码成功 | 绿色常亮约 500 ms，随后进入连接状态 |
| 配码超时或验证失败 | 红色闪 3 次 |
| 双端解绑成功 | 黄色闪 2 次 |
| 2.4G 已连接 | 沿用无线连接指示；不长期占用 RGB 灯效 |

## 首次配对

1. 首次给接收器烧录接收器固件后插入电脑。接收器没有有效绑定记录，会自动进入 60 秒蓝色双闪窗口。
2. 把三模键盘切到 2.4G，插入 USB，在 Studio 的“2.4G 无线与接收器”点击“开始配码”。
3. 接收器和键盘通过 WCH RF FAST 的 Host/Device 绑定流程交换 PeerInfo，并分别写入 DataFlash。
4. Studio 显示“已绑定”或“已连接”后，断电重启两端确认绑定能够恢复。当前没有 RGB 状态提示，以 Studio 状态为准。

默认 FN2 长按是模式相关的无线维护动作：BLE 下清除绑定，2.4G 下进入配码，USB 下不执行破坏性操作。Studio 仍保留原有动作编号和帧格式。日常配码不依赖 BOOT 引脚，PB22 改接 PB11 仅保留给恢复刷写。

## 清除与重新配码

当前“清除绑定”只清除 Studio 正在连接的一端，没有伪装成已经完成双端事务。
手动重新配码遵循 profile transaction 规则：配码失败或超时保留原绑定，只有
RFBound 成功回调后才提交新绑定；这避免了失败一次就把键盘变成未绑定状态：

- 清除接收器后，接收器不是废设备。它清空本地记录并立即自动开启 60 秒配码窗口。
- 清除键盘后，键盘进入未绑定状态。接收器仍保存旧记录，因此还需要连接接收器执行一次“清除绑定”，再让两端重新配码。

常规换键盘、换接收器或转售前，应分别清除两端，再重新配码。双端确认式解绑属于后续增强项。

## Studio 与 HID 协议

Studio 通过 HID Vendor 接口发现设备及其 collection；它不读取或展示原始 HID report descriptor 作为配置协议。设备信息、角色、配码状态、轮询率和配码控制都走有版本的 Vendor HID 命令：

```text
RADIO_CAPS           当前角色、是否启用 RF、支持的轮询率
RADIO_PAIR_STATUS    unbound / pairing / bound / connected / inconsistent
RADIO_PAIR_START     开启 60 秒配码窗口
RADIO_PAIR_CANCEL    取消本次窗口
RADIO_PAIR_CLEAR     发起双端解绑事务
RADIO_POLL_RATE_GET  读取接收器 USB 轮询率
RADIO_POLL_RATE_SET  设置 125/250/500/1000 Hz
RADIO_REMOTE_CAPS    读取远端键盘型号与能力
```

绑定数据只向 Studio 返回角色、状态、会话编号和非敏感设备标识，不通过网页读取或导出 PeerInfo。

## 远端配置透传协议

接收器不模拟一份键盘配置。Studio 发给接收器的 `SYS_INFO`、`KEYMAP_*`、
`LAYER_*`、`RGB_*`、`FNKEY_*`、`CFG_OS_*`、`BATTERY`、`MACRO_*` 和保存命令，
由接收器通过独立管理通道转发给已配对键盘；键盘仍调用与 USB/BLE 相同的
`KBD_Command_Process()`，所以校验、DataFlash 保存和响应格式只有一套实现。

管理通道采用会话内单事务、停等式分片协议：

1. 每个 USB 请求分配非零 `transaction`，并保留原始 `command/sub/length/data`。
2. 请求或响应每片最多携带 20 字节，带协议版本、事务号、命令、分片序号、总片数
   和 `FIRST/LAST/ERROR` 标志；外层 RF 帧继续使用 session、sequence 和 CRC16。
3. 任一时刻只允许一个管理事务。中间分片收到明确 `MGMT_ACK` 后才发送下一片；
   未确认分片按约 4 ms 间隔最多提交 3 次。
4. 键盘以 `transaction + command + sub` 识别重复请求，并在短期缓存最近响应。
   接收器重发同一请求时，键盘重发缓存响应而不重复执行写 Flash 等有副作用命令。
5. 接收器按事务号和分片序号重组完整响应，只有完整且命令匹配的响应才返回 USB。

### 透传失败的根因与最终修复

早期实现收到最后一个请求分片后，键盘连续向 RFBound Device TX 队列提交两包：
先发独立 `MGMT_ACK`，紧接着再发真正的 `MGMT_RESPONSE`。实机日志稳定表现为
接收器 `TX=1/1`、`RX=0/0`：最后请求已经到达键盘，但 Host 经常只收到 ACK，
随后提交的响应在 RFBound DMA/时序竞争中丢失或长期不出队。HID 输入使用另一种
数据流，所以会同时出现“键盘可以打字，但 Studio 远端能力超时”。

最终协议把**完整命令响应本身定义为最后一个请求分片的确认**：只有非末片请求
发送独立 ACK，末片重组后直接执行命令并发送响应。这样末片不再产生背靠背的
ACK + RESPONSE，Host 收到响应既证明请求完整到达，也取得了命令结果。结合停等
重传和键盘端响应缓存，读命令与改键、改灯等写命令都能可靠完成，并避免重试造成
重复保存。这是透传恢复的核心原因，不是单纯延长网页超时。

## 重连与永久 BUSY 恢复算法

管理事务只能属于创建它的那一次 RFBound 链路会话，不能跨重连持久化。此前键盘
关机超时后，旧事务的 callback、TX active 标志或已武装的 TX DMA descriptor 可能
留在内存中；新请求看到这些全局状态便持续返回 `ERR_BUSY`。仅保存 peer 身份只能
恢复 HID 链路，不能恢复这一半完成的管理事务，因此必须同时处理身份持久化和会话
状态失效。

当前采用“持久化绑定 + 易失会话代次清理”的恢复算法：

1. DataFlash 只持久化 local/peer、RFBound device ID、绑定 generation 和校验值；
   管理事务号、分片游标、ACK、callback、响应缓存和 DMA 所有权全部是易失会话状态。
2. 键盘与接收器在 RFBound `SUCCESS`、`bleTimeout`、`FAILURE` 等链路边界只设置
   `management_session_reset_pending`。回调中不直接做复杂清理，主循环原子消费该
   标志，避免 RF 中断与管理发送同时修改结构体。
3. 主循环同时清空 RX/TX 重组状态、pending command、ACK、callback、超时起点和
   重复响应缓存。接收器还调用 `RFRole_ClearTxData()`，重置全部 Host TX DMA
   descriptor，并把 `pDMATxGet` 复位到环首，确保旧会话的武装描述符不会阻塞新包。
4. 若单次事务自身超时，先保存 callback 与事务号并向等待中的 USB 请求返回超时，
   再重置 TX DMA 环和管理状态。新命令只有在 `callback == NULL && tx.active == false`
   时进入；忙检查发生在安装新 callback 之前，避免覆盖旧 callback 或误删新事务。
5. 链路恢复后清除缓存的远端能力，Studio 串行重新执行能力发现和配置读取；失败后
   等待 5 秒再恢复，不并发堆叠 `RADIO_REMOTE_CAPS`、`KEYMAP_GET` 等请求。

因此重连不需要拔插接收器：RFBound 使用持久化 peer 恢复 HID，会话清理保证第一笔
新管理命令从空闲状态开始，Studio 再重新发现键盘能力。实机已经验证键盘关机至链路
超时、重新开机后，HID 与远端读写均能自行恢复。

## 实现边界

本次状态机按公开成熟实现的边界组织，而不是把它们的代码复制进固件：

- QMK `quantum/split_common/transport.c`：传输事务成功与连接状态分离，应用层
  不把一次发送成功当作对端已连接。
- ZMK settings/profile 机制：绑定 profile 持久化，重新配码是显式事务，失败不
  覆盖现有 profile；连接指示与按键 RGB 效果分开管理。
- WCH CH59x RF FAST SDK 的 `RFBound_StartHost/StartDevice`：继续使用其 Host /
  Device、跳频、确认和重发实现，仓库只在上层增加 profile、帧序号和 CRC 校验。

本分支已提供可链接的 RF FAST Host/Device、接收器 USB HID 和远端配置路径，并直接
复用 WCH 官方 RF FAST 库的绑定、跳频、确认和重发状态机。应用层额外使用
magic/version/session/sequence/CRC16 校验。已完成实机绑定、HID、远端配置读写、
键盘断电重连和接收器硬件替换验证；尚未完成的发布验收包括抗干扰距离、长期丢包率、
功耗、应用层加密、双端确认式解绑和批量硬件测试。旧固件仍不会误开启 2.4G 功能。

## 发布前的断联审计结论

当前基线保留 WCH RFBound 官方链路恢复语义，并在其上增加管理事务的会话失效与
DMA 清理；这两层不能混为一谈。RF 链路层仍由 `bleTimeout` 执行库内恢复，只有
`FAILURE` 才按官方流程重新启动保存的 peer。应用层没有重新引入 KEEPALIVE、短周期
看门狗或在 `bleTimeout` 时主动执行 `RFRole_Shut -> RF_LibInit`。

管理层的 session reset 只丢弃已经失去归属的配置事务，不重启 RF role，也不改变
持久化绑定。它解决的是重连后配置通道永久 `ERR_BUSY`，不能缩短 RFBound 判断物理
断电所需的底层时间。因此“重连后 HID 与配置可自行恢复”已经实机确认，而“键盘突然
断电后必定在几百毫秒内停止最后按键”仍不是当前版本的承诺。
