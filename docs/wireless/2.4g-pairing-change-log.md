# 2.4G 配码开发分支变更日志

分支：`feat/ch592-2g4-pairing`  
基线：`fix/ch592-power-wake` / CH592F `3.1.41`

## 本次加入

- 定义 2.4G Vendor HID 命令：能力查询、配码状态、开始/取消/清除配码、接收器 USB 轮询率读写。
- `SYS_INFO` 增加 RF 能力与设备角色位。旧固件和当前 BLE-only 键盘均返回未启用，Studio 不展示不可用的 2.4G 控件。
- Studio 预留“2.4G 无线与接收器”页面以及 `125/250/500/1000 Hz` 轮询率接口，默认设计值为 `1000 Hz`。
- 增加仅在 RF-enabled 固件显示的 FN 长按动作“进入 2.4G 配码”；默认配置不绑定该动作。
- 键盘模式层新增正式的 `KBD_WORK_MODE_2G4=2` 和 `KBD_Radio2G4_*` 后端边界：启动模式、模式切换、FN 配码、按键报告都会经过该边界；普通构建后端安全返回“不支持”。
- 确定首次无绑定接收器自动 60 秒配码、双端解绑事务和强制清除后的恢复规则。

## 后续实现

- 增加独立 RF-only 键盘目标，链接 WCH RF FAST Device 库并发送键盘、鼠标和消费者控制报告。
- 增加 CH592F RF Host + USB HID 接收器目标，PID 为 `0x2108`；无绑定时自动配码，支持 DataFlash 绑定保存与 `125/250/500/1000 Hz` 设置。
- Studio 同时识别键盘 PID `0x2107` 和接收器 PID `0x2108`，按设备角色显示配码和轮询率控制。
- RF 帧加入 magic、版本、序号、长度和 CRC16 校验；设备类型和固定键盘 ID 与 WCH 官方键盘示例保持一致。
- 普通 USB/BLE release 保持原 10 ms USB 键盘端点；只有接收器使用 1 ms 端点。
- 接收器绑定存储迁移到 `0x5000/0x5100` 双槽，避开键盘已有的配置与宏数据区；新增版本、代数、CRC16、回读校验和断链全释放。
- 接收器 USB/RF 中断改为只排队和置标志，Flash、配码控制、USB 报告发送在主循环执行；三类 HID 报告使用环形队列。看门狗在当前版本没有启用，待 RF 启动稳定后再评估。
- 接收器首刷产物改为 `CH592F-RECEIVER-full.hex`，包含 `0x0000` JumpIAP、`0x1000` 接收器应用和 `0x6D000` IAP；禁止将仅含应用的 `CH592F.hex` 用于整片擦除后的首刷。

## 未声称完成的部分

- 当前已通过交叉编译和静态协议核对，但尚未用两块 CH592F 实物确认首次配码与输入链路。
- USB 诊断接收器已确认可稳定枚举和响应 Studio，但它刻意不启动 RF；正式 RF 接收器启动 RF 后 USB 会掉线，正在定位，不能视为可配码版本。
- RGB 配码提示、应用层加密、双端确认式解绑、距离/丢包率/功耗 benchmark 仍待硬件联调。
- 当前 2.4G 键盘是独立 RF-only 镜像；受 WCH 预编译库底层符号冲突和 RAM 限制，尚不是 BLE + 2.4G 同镜像三模方案。

## 2026-08-21 RF 诊断日志收敛

- Studio 终端对后台 `SYS_STATUS` 和 `LOG_GET` 查询做内容去重，连续相同
  状态不再每 2 秒刷屏；状态变化、命令错误和设备事件仍然保留。
- 接收器新增配码开始、RFBound 成功/超时/失败、首个有效 RF 帧和应用链路
  断开事件，并由网页终端读取显示。
- 接收器状态为“已绑定”但“链路未确认”时，日志会明确区分“没有收到有效帧”
  与“USB HID 已发送失败”，不再依赖 RGB 颜色推断连接状态。
- 实机日志确认 RFBound 出现 `SUCCESS -> bleTimeout -> SUCCESS` 循环。根因是
  配码成功后 Host speed list 仍使用只代表可绑定状态的设备号 `7`；已按 WCH
  官方接收器回调改为实际分配的 `devId`，使 Host 从配码时隙进入固定 peer 的
  正常通信时隙。重复 SUCCESS/timeout 事件在单次 Host 会话内只记录一次。
- 后续实机确认首次配码和 HID 首帧可用，但断电重启后无法恢复。接收器过滤
  状态现拆分为三段：未限定 peer 的 `BINDABLE(ID=7)`、限定已保存 peer 的
  `RECONNECT(ID=7)`、成功后使用实际设备号的 `ACTIVE(devId)`，与 WCH 官方
  `RF_START_PEER_BOUND_EVENT -> SUCCESS callback` 顺序一致。
- 手动清除绑定后保持 `UNBOUND`，不再自动开放配码窗口，防止仍通电的旧键盘
  立即重新绑定而表现为“清不掉”；清除时同时丢弃尚未提交的绑定回调。无绑定
  接收器冷启动时仍保留自动配码，手动清除后需显式点击“开始配码”。
- 实机随后确认接收器能收到键盘 HID 首帧，但数秒后再次超时。键盘端在
  RFBound `SUCCESS` 后现立即提交并关闭手动配码事务；后续 `bleTimeout` 按
  正常链路监督/重连处理，不再退回会暂停应用 keepalive 的手动配码状态。
- 键盘 `RADIO_PAIR_STATUS v2` 增加 TX 入队、DMA 忙、TX_FINISH、最近 TX 与
  16 个 TX 描述符占用量，用于区分发送队列堵塞和 RFBound 停止调度；Studio
  面板和 Debug Terminal 均解析这些字段。
- Studio 对后台 `SYS_STATUS / RADIO_CAPS / RADIO_PAIR_STATUS /
  RADIO_POLL_RATE_GET / LOG_GET` 查询统一按 10 秒限流显示，避免动态时间字段
  造成终端再次堆满；控制命令、错误与设备 RF 事件不受影响。

## 2026-08-22 键盘重连发送队列修正

- 实机诊断确认双端本机 ID、对端 ID 与指纹完全匹配，问题不在配对身份；键盘
  端表现为 TX 已入队 16、TX_FINISH 为 0、DMA 描述符长期 `16/16`，接收器
  因此在重启后始终收不到首个应用帧。
- 根因是键盘此前允许在 `BOUND`（仅有持久化 peer、RF 会话尚未建立）状态发送
  HID 和 100 ms 保活，约 1.6 秒即可提前占满 16 个 TX 描述符。现与 WCH 官方
  `rf_device.c` 的状态边界一致：只有 `RFBound SUCCESS` 后进入 `CONNECTED`，
  才允许应用数据入队。
- `bleTimeout` 后只在 RF 回调中设置恢复标志，随后由主循环调用 WCH 官方
  `RFRole_ClearTxData(deviceId)` 清理遗留队列；没有直接改写 DMA 描述符状态。
- 自动重连成功时，仅在 `deviceId` 或 peer 地址发生变化时写入绑定 DataFlash，
  与 WCH 官方示例一致，避免每次重连都擦写绑定页。
- 2.4G 5KEY 与 KNOB 固件均已重新编译并生成完整 ISP 镜像；本轮改动只涉及
  键盘端，仍需实机确认重启后描述符不会卡在 `16/16`、接收器可持续收到保活
  与 HID 帧。

## 2026-08-22 输入失控与断链释放修正

- 实机确认基础配码、重连和 HID 链路可用；压力场景仍可能出现 TX 描述符占满、
  松开报告延迟，表现为操作系统持续连发同一按键，或短暂断触后等待队列排空。
- 键盘核心在传输忙时不再停止读取后续物理事件，而是持续更新并保留“最新完整
  键盘状态”；因此松开事件可以覆盖待发送的旧按下状态，传输恢复后优先同步
  当前真实状态，而不是回放积压事件。
- WCH TX 环的应用占用上限设为 4/16，避免短时干扰把全部描述符填满；100 ms
  保活包只在 TX 环完全空闲时入队，不再与按键状态争抢队列容量。
- 2.4G 的 `BOUND` 仅表示已有 peer、正在重连，不再被上层视为可输入状态；
  重连期间的操作被丢弃，连接恢复后先同步全释放，避免重放断线期间的按键。
- 接收器应用链路看门狗从 2 秒缩短到 300 ms（连续丢失约三个 100 ms 保活），
  超时即清空接收器报告队列并向 USB 主机发送键盘、鼠标和媒体键全释放，目标
  是在操作系统启动按键连发前解除按下状态。
- 取消 RF 回调中的蓝色配码长覆盖与连接成功橙色短覆盖。指示灯由统一状态机
  管理：蓝色表示未绑定/配码，橙色表示已绑定但正在重连，绿色表示可发送；
  回调失败仅排队红色短闪，由主循环实际更新 WS2812。
- 5KEY、KNOB、Receiver 和普通 USB/BLE 两种布局均已构建通过。此版需要同时
  重刷键盘与接收器，并通过快速点按、持续按住、接收器热拔插和无线干扰场景
  做实机验收后，才能确定 300 ms 看门狗是否需要调整。

### 长按回归修正

- 首版队列保护要求 TX 描述符完全空闲才发送保活，但 WCH RF 正常流水线也可能
  长期占用多个描述符；长按期间没有新按键边沿，保活因此可能被完全抑制，导致
  接收器错误地按 300 ms 看门狗释放正在按住的键。
- 保活现允许在应用占用低于 `3/16` 时入队，同时始终为下一个按键变化（尤其是
  松开）保留至少一个应用槽；总应用占用上限仍为 `4/16`。
- 接收器断链全释放窗口调整为 500 ms，即连续丢失约五个 100 ms 保活后释放。
  这仍显著短于旧版 2 秒，但对 WCH 调度和跳频抖动留出了更合理的余量。

### WCH、ZMK 与 QMK 行为复核

- 再次逐行核对 WCH CH592 官方 `rf_device.c`、`trans.c` 与 Dongle `rf.c`。
  应用数据仍只允许在 `RF_CON_CONNECTED` 后发送；发送前采用官方的“当前 TX
  描述符和下一描述符都空闲”判断，始终为 RF 库保留一个描述符。移除项目自行
  设定的 `4/16` 应用上限，避免正常 RF 流水线占用三个槽时错误压住长按保活；
  该规则最多使用 `15/16`，不会再次填满整个 TX 环。
- 接收器断链全释放窗口改为 WCH 官方 `RF_REPORT_DISCONNECT_DELAY = 160 * 4`
  TMOS tick 对应的约 400 ms。超时后仍由接收器主动向 USB 主机发送全零键盘、
  鼠标和媒体报告，解决无线断开后电脑仍保留最后一个按下状态的问题。
- 核对 ZMK `app/src/endpoints.c`：切换/丢失 endpoint 时先调用
  `zmk_endpoint_clear_reports()`，源码注释明确用于防止按键留在旧 endpoint；
  核对 QMK `tmk_core/protocol/host.c`：切换活动连接驱动时同样执行
  `clear_keyboard()`。因此本项目保持“真正断链后全释放、重连不重放断线前
  按键”的安全语义。
- 正常连接中的长按没有固件时长或次数上限：键盘发送的是完整按下状态，电脑
  依据该状态持续执行系统键盘重复；100 ms RF 保活只维持链路，不制造额外按键
  次数。只有确认断链约 400 ms 后才执行安全释放，松开再按可重新开始输入。
- WCH RFBound 是本项目实际使用的底层协议；ZMK/QMK 仅用于核对 HID 状态和
  endpoint 安全策略，不能据此声称本项目的私有 2.4G 协议与其完全相同。

### 撤销应用层看门狗，采用 RFBound 延迟断开

- 实机日志连续出现“收到首个有效 RF 帧 -> 应用链路断开 -> 再次收到有效帧”，
  证明此前用“400 ms 没有应用 HID/keepalive 包”判断断链是错误的：RFBound
  会话仍在自动恢复，而应用看门狗把正常的空闲或长按错误标记为断开。
- 删除键盘自行生成的周期应用 keepalive，以及接收器依据应用包间隔判断连接的
  看门狗。空闲键盘没有新 HID 报告是正常状态，链路监督只由实际使用的 WCH
  RFBound 状态机负责。
- 键盘收到 `bleTimeout` 时只暂停 RF 发送，仍保持上层 `CONNECTED` 和当前按键
  状态；400 ms 内收到 `SUCCESS` 会取消断开并继续同步。这对应 WCH 官方
  `RF_REPORT_DISCONNECT_DELAY` 行为，短暂跳频/重连不再截断正常长按。
- 接收器也只在 RFBound `bleTimeout/FAILURE` 后启动 400 ms 延迟断开，期间
  `SUCCESS` 或任何有效 RF 帧都会取消。持续超时才切换为 `BOUND` 并全释放。
- 接收器新增独立 Timer2 1 ms 防卡键路径。确认持续断链后，零键盘/鼠标/媒体
  报告直接提交到 USB endpoint，不依赖可能正忙于 RF 重连的 TMOS 主循环；
  Debug Terminal 的“应用链路断开”现在只代表 RFBound 持续超时，而不是没有
  新应用按键包。

### 接收器热插拔自动重连

- 修复已绑定键盘在接收器拔出后永久停在 `BOUND`、必须重启键盘才能恢复的
  问题。根因是 `bleTimeout` 后只等待 RFBound 内部短时恢复，上层没有像 WCH
  官方三模示例 `RF_ReStart()` 那样重新初始化 RF role 并再次启动已绑定设备。
- 首次超时保留约 400 ms 给 RFBound 内部快速恢复；仍未恢复时执行
  `RFRole_Shut -> RF_LibInit -> RFBound_StartDevice`，始终携带 DataFlash 中保存
  的原 peer，不清除绑定，也不开放配码窗口。
- 重试采用有界退避：开始两次约 250 ms，随后约 1 s，长期不可用时约 5 s。
  接收器重新插入后键盘会自动恢复，不再要求重启键盘或重新配码。
- 手动开始/取消配码、清除绑定和停止 2.4G 时会同步取消旧的延时重连任务，
  防止清除后的 peer 被旧任务重新启动。连接成功后重试计数归零。
- 断线期间的按键不排队、不在恢复后重放；接收器确认断链后向 USB 主机提交
  全释放。恢复连接后需要松开再按，行为与成熟无线键盘切换 endpoint 时的安全
  处理一致。

### 按 WCH 官方状态机修正热插拔重连

- 实机显示上一版接收器重插后键盘周期红闪且不能恢复。复核 WCH 官方
  `rf_device.c` 后确认：`bleTimeout` 表示 RFBound 已进入内部自动恢复流程，
  官方不会在这个回调上执行 `RFRole_Shut/RF_LibInit`；上一版的外部定时重启会
  反复打断库内恢复，因此撤销该逻辑。
- 键盘现在严格采用官方事件模型：`bleTimeout` 只暂停应用发送并等待 RFBound
  自动恢复；只有 `FAILURE` 才从主循环重新执行保存 peer 的
  `RFBound_StartDevice`。红色失败提示不再由正常的 `bleTimeout` 触发。
- 接收器补齐 WCH Dongle 官方的失败恢复路径：`FAILURE` 后清理旧 RX 数据，并
  重新启动使用保存 peer 过滤列表的 Host。Host 启动结构中的 `PeerInfo` 保持为
  零，peer 只由 `RFBound_SetSpeedType` 的列表管理，与官方 `rf.c` 一致。
- QMK/ZMK 用于核对 endpoint 切换时清空旧 HID 报告、恢复后不重放断线输入的
  上层原则；它们没有可直接移植到 CH592F RFBound 的通用私有 2.4G 重连算法。

### 接收器名称与失败灯光修正

- 接收器 USB PID 已独立为 `0x2108`，但构建配置仍强制复用键盘产品字符串
  `BinaryKeyboard5KEY`，导致操作系统和 Studio 把接收器显示成基础款键盘。现将
  接收器 USB 产品字符串改为 `BinaryKeyboardReceiver`；Studio 同时根据接收器
  能力显示“2.4G 接收器”，不再附加键盘型号。
- RF `FAILURE` 保留一次 300 ms 红色短闪，随后由状态机继续显示橙色重连；
  同一次断线中的重复失败不重新触发红灯，避免看起来像常亮。连接成功会主动
  取消尚未结束的红色覆盖，再显示绿色连接确认。绿色按现有省电设计显示约
  600 ms 后熄灭，橙色重连则持续呼吸。
- 红闪结束和连接成功均使用 RTC 判断并立即刷新 WS2812，不依赖 RGB 的 TMOS
  周期任务。修复仅清除 `s_flash_active`、但物理灯仍保持最后一次红色写入的
  问题；即使 RF 恢复期间 RGB 定时任务停顿，也会明确写回橙色或绿色。
- 实机进一步确认启动绿灯、断开红灯和重连暗绿都会永久保持，证明 2.4G 下
  RGB 的 TMOS 20 ms 事件没有稳定续约。2.4G 构建现改为由主循环使用 RTC 每
  20 ms 调用 RGB 引擎；普通 USB/BLE 构建仍使用原 TMOS 任务。呼吸、短闪和
  自动熄灭不再依赖 RFBound 同时占用的 Timer3/TMOS 调度。
- 后续实机仍出现颜色锁存。2.4G 的 RGB 节拍改由已用于按键扫描、消抖和长按
  的 Timer0 1 ms 时基累计，主循环每 20 ms 消费一次，ISR 不操作 WS2812 DMA。
  同时在 RGB 调度关闭的 LIGHT 状态拒绝 RF 回调直接写灯，防止休眠后状态变化
  重新点亮灯珠并留下永久颜色。
- 接收器发布前可靠性优化：USB 枚举改为异步，不再阻塞 RF Host 启动；断链释放
  仅由 Timer2 中断置位标志，USB 报告统一回主循环发送；绑定槽校验 peer 与
  device ID 的一致性；状态查询返回 RFBound 保留 Host ID；键盘报告队列满时
  压缩为最新完整状态，避免旧按下报告滞留；USB 轮询相位使用 64 位累计，避免
  长时间阻塞后的乘法溢出。
- 针对键盘突然断电后的 HID 卡键增加链路保护：RFBound 超时即使状态已回落为
  BOUND，只要当前 session 曾收到有效应用帧仍会触发释放；新增
  `LINK_TIMEOUT`、`HID_RELEASE_QUEUED`、`HID_RELEASE_SENT` 和
  `HID_RELEASE_BUSY` 诊断事件，用于区分“未识别断联”和“识别后 USB 未接受
  全零报告”。
